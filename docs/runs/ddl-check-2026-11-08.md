# Result

The schema check now runs on the binary's own stack: it calls `store.Open`
(which registers sqlite-vec through `vec.Auto()` before any DDL and applies
`migrations/0001_init.sql` + `0002_state.sql`) instead of applying SQL through
a separate Python `sqlite3` connection.

What it pins:

- **Tables** — `chunks`, `chunks_fts`, `chunks_vec`, `schema_migrations`,
  `source_state`, `source_items` all exist after the runner.
- **FTS5 stored columns** — a row written by `store.ReplaceItemChunks` reads
  back `title`, `body`, and `tags` (a `content=''` table returns nothing here)
  and a `MATCH` query joins to `chunks` on `chunk_id`.
- **vec0 width and KNN** — `chunks_vec`'s DDL declares
  `float[store.EmbeddingDims]`, an embedding written through
  `store.WriteEmbeddings` is returned by `store.SearchVectors`, and the raw
  table rejects a short vector with
  `Dimension mismatch for inserted vector ... Expected 768 dimensions but received 767`.

**This supersedes the `check-ddl` capture from 2026-10-21, whose
`scripts/check-ddl.py` command never existed in the repository.**

## Mutation check

The assertions were verified against deliberately broken copies of
`migrations/0001_init.sql` (restored afterwards):

- `chunks_fts ... content=''` → `TestSchemaDDL/fts5_stored_columns_and_join-back`
  fails with `chunks_fts stored columns must read back (contentless tables
  cannot): sql: no rows in result set`.
- `chunks_vec(embedding float[384])` → `TestSchemaDDL/vec0_width_and_knn_round-trip`
  fails on both the DDL width assertion and the `store.WriteEmbeddings`
  insert (`Expected 384 dimensions but received 768`).
