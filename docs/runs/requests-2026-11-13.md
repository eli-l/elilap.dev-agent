# Result

The deferred-question workflow works end to end, with the operator side and
the peer side both exercised against a real `agent serve` and the live
949-chunk index. `docs/requests.md` is the reference; `PLAN.md` Decision 26
and Phase 5 are the scope.

What the run pinned:

- **Discovery**: the card advertises `pushNotifications: true` and the
  `knowledge-request/v1` extension only because the server was started with
  `--push-notifications` and has a request store open. Without them the card
  says `false` and the push methods answer `-32003`.
- **Submission**: a single `message/send` with
  `metadata.knowledgeRequest` returned a `Task` in `submitted` with the peer's
  `contextId` echoed. No model call ran, and the question text appeared only
  in the owner inbox and the owner webhook.
- **Owner notification**: the queued webhook delivered
  `knowledge_request.created` immediately, off the request path.
- **Resolution**: `agent requests resolve --no-ask` stored the answer and
  source URL, flipped the task to `completed`, and delivered the completed
  `Task` to the peer webhook in one attempt with the shared token header and
  an HMAC signature.
- **Task methods**: `tasks/get` returned `completed` with the `answer`
  artifact and evidence metadata; `tasks/cancel` on a closed request returned
  `-32002` as documented.

The `--no-ask` path was used in this capture because the corpus does not
contain an answer to the fixture question. The default `resolve` path (which
runs the grounded loop and refuses while the corpus refuses) is covered by
`cmd/agent` tests and by the wire tests in `internal/a2a`.

## Boundaries confirmed

- `--bind-public --push-allow-insecure` exits 2 with
  `--push-allow-insecure is refused with --bind-public`.
- `--bind-public` with `--request-quota 0` exits 2 (a public inbox needs a
  daily cap).
- `requests.db` lives beside the index, so the index rebuild path
  (`rm data/index.db*`) cannot erase a submitted question.
